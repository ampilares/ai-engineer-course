# Week 4: AI-assisted engineering and prototyping

You will deliver one small software change and prove what it does. AI can accelerate reading and editing code, but the acceptance criteria, runtime permissions, and review remain engineering responsibilities. Business owners use the same process with a smaller implementation surface.

## 1. Give the coding tool a bounded job

Start with a reproducible problem. "Improve the report" does not identify a defect. "Reject duplicate IDs with conflicting amounts instead of counting the first row" names an observable behaviour. Write a failing example, expected result, affected boundary, and a way to test it before asking for implementation.

Provide the repository entry point, relevant files, test command, constraints, and finish criteria. Ask the coding tool to inspect these files and explain the proposed change. A focused diff is easier to assess than a broad rewrite mixed with unrelated formatting.

A useful task brief for this week's exercise is:

```text
The report must identify conflicting duplicate transaction IDs.
Read the supplied reference implementation and its tests.
Explain the current behaviour before proposing a change.
Add a conflict case in a separate fixture copy.
Reject the conflicting event; preserve both source rows in review evidence.
Do not change the accepted treatment of exact duplicate copies.
Run the relevant tests and show the resulting diff.
Do not install new dependencies or contact external services for this task.
```

The boundaries are deliberately narrow. If the implementation needs a dependency, discuss its purpose and provenance instead of accepting an invented package name. If the assistant claims a test passed, inspect the command and output. Reading a test file is not running it.

Choose a tool using [Codex's official learning resources](https://developers.openai.com/learn/codex), [Claude Code's overview](https://code.claude.com/docs/en/overview), or [Cursor's Agent documentation](https://cursor.com/docs/agent/overview). The core skills in this lesson are independent of which interface you use.

## 2. Review behaviour, not just the generated diff

Review in layers. First check the specification: does the change solve the intended problem? Then check inputs and edge cases. Then examine failure handling, data access, and side effects. Finally inspect maintainability: naming, duplication, and whether future readers can find the rule.

A meaningful regression test fails on the old broken behaviour and passes after the fix. Asserting that a function returns something is weak evidence. A test that inserts two rows with the same ID and different amounts, then verifies both are excluded and a conflict is visible, tests the business requirement.

Do not trust a generated test merely because it agrees with generated code. Derive expected results from the requirement. If the assistant implements an incorrect rule and writes a test expecting that rule, green tests can reinforce the mistake. Use a manually checked counterexample and ask a reviewer to challenge it.

### Worked review

An agent fixes duplicate billing by discarding every repeated ID, including the first event. That prevents double counting but loses the legitimate transaction. The correct result for an exact duplicate is one event. For two conflicting versions, the appropriate result in this course is review, with no amount included until resolved. These are different cases and need different tests.

Record the current commit or file snapshot before changing behaviour. Reversal may be a Git revert, a deployment rollback, or disabling a new workflow. Reverting code does not necessarily undo messages already sent or records already changed. Keep this exercise local and use generated drafts as its only outputs.

## 3. Studio and the first practical gate

### Engineering route

1. Choose a small reporting improvement or a defect in your own authorised project. State three acceptance cases.
2. Reproduce the current behaviour and ask the coding assistant to inspect the relevant files.
3. Review its plan, implement the change, and inspect the diff.
4. Run a regression test, normal-case test, and failure-case test.
5. Revert or disable the change in a disposable copy, then restore it. Record what the reversal does and does not undo.

### Business-owner route

1. Specify a request-intake or report-review prototype using [the task brief template](../templates/task-brief.md).
2. Use the supplied [local review prototype](../labs/review-prototype.html), or ask your approved coding tool to modify a copy. It must run without connecting to a real customer account.
3. Test a complete request, an empty field, a mixed request, and a refund request.
4. Inspect whether the interface distinguishes drafts from completed actions. Record any misleading label.
5. Ask another person to use it and record one misunderstanding, then revise the specification or interface.

### Evidence and reflection

Submit the task brief, before/after behaviour, reviewed diff or prototype, test output, and a rollback note. Explain one AI suggestion you rejected. Pass the Week 4 gate when you can independently verify the artifact and make a substantive correction without relying on the assistant's assurance.

The reference lab already handles conflicting duplicates. For the supplied project, make the optional improvement concrete by adding a grouped review summary by reason, preserving individual source rows, and testing its counts. Do not claim to have fixed a defect that was not present; record whether your work is a new feature, a reproduction exercise, or a real fix.
