# Week 14: Capstone implementation

The capstone is one useful system built from the work you have already completed. This week closes the gaps between separate labs and a reproducible end-to-end process. Avoid adding a new platform simply to make the final demo look more advanced.

## 1. Freeze scope and acceptance criteria

Write a one-page contract with the process owner. It must identify users, inputs, outputs, allowed actions, data boundaries, review responsibility, and the decision the system improves. Include a non-goal that prevents the project from expanding during the pilot.

For Harbour, the contract might be: "Prepare a weekly brief from authorised operating records, validate totals, cite effective policy, and queue unresolved items for Maya. Do not contact customers, approve refunds, or modify the ledger." A support-triage project can use the same structure with a different output.

Define measurable criteria before the final evaluation. Specify ordinary task success, mandatory boundary checks, maximum intervention workload, latency, cost, and recovery. Choose thresholds that make sense for the task. A classroom minimum of thirty evaluation cases is a floor for finding problems, not a statistical guarantee.

Freeze at least twenty development cases and ten held-out cases. Store hashes or a version identifier for the case files. Keep held-out material out of prompts, retrieval indexes, skills, and examples. Public course cases are suitable for rehearsal; use independently authored variants for an assessed capstone.

### Worked acceptance contract

The weekly brief must reconcile every input row, use authorised effective policies, and expose all unresolved data. It must never execute a customer-facing action. A report counts as successful only after the reviewer completes the checking protocol. A blocked export test is mandatory regardless of the average quality score. These statements let two reviewers reach the same decision.

## 2. Complete the vertical slice

A vertical slice carries one input through every required step: intake, validation, AI processing, verification, review, and output recording. It is better evidence than several impressive components that cannot be used together.

For each boundary, record the schema, identity, error behaviour, and owner. Does an invalid input become a visible review item? Does an interrupted run preserve enough state to resume? Does an approved action remain bound to its exact payload? Can the operator tell whether an external action happened before a timeout?

Use the smallest architecture that meets the contract. A fixed workflow with one model call may be easier to assess than an agent with many tools. If you choose an agent, explain what useful decision it makes and why a fixed sequence is insufficient. If you choose retrieval, identify the source owner and update path. If the project needs neither, do not add it merely to demonstrate terminology.

### Integration review

Trace one case by ID through the system. Collect its source version, prompt version, model response status, validation outcome, reviewer decision, final artifact, duration, and cost. Avoid copying sensitive raw content into every stage. A missing case ID between two components is a debugging and audit problem worth fixing before the pilot.

Write a repeatable setup command or workflow-import procedure. A secret value must be supplied through the environment or approved credential store; it should not be present in the repository, screenshot, or example output. List required accounts and capabilities without implying that every learner has them.

## 3. Studio and implementation review

### Engineering route

1. Complete the vertical slice and test it on three development cases: normal, ambiguous, and unavailable dependency.
2. Run automated interface, business-rule, permission, and recovery checks appropriate to your architecture.
3. Package the setup, fixture inputs, and operational commands so another engineer can reproduce the run.
4. Review the diff for broad permissions, unnecessary dependencies, and unrelated changes.
5. Record remaining limitations and choose what is required before the pilot can start.

### Business-owner route

1. Complete the configured workflow or assistant and test the staff-facing process from intake to review.
2. Verify the reviewer can see evidence, correct a result, reject an action, and locate unresolved work.
3. Ask a second person to follow the operating procedure with a new case.
4. Check the cost and support assumptions with the implementation owner.
5. Sign off the bounded pilot scope, or narrow it until the acceptance criteria are achievable.

### Required submission

Submit the working candidate, scope contract, frozen case-set record, integration trace, reproducible setup, and open-issues list. Use the [capstone requirements](../../CAPSTONE.md) as the submission checklist. The checkpoint decision is ready for pilot, ready with stated restrictions, or hold for a named issue.

If the application has no live credentials, demonstrate the surrounding system with fixtures and clearly label the AI-quality measurement as pending. Do not pass off a deterministic replay as a live agent result. A capstone using a supervised assistant can be fully valid if it is honestly scoped and its actual workflow is evaluated.
