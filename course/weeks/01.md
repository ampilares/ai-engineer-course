# Week 1: AI foundations and useful work

This week you will choose one task, describe acceptable work, and record a baseline. Engineers should budget 8-10 hours; business owners 5-7 hours. Begin with the [Harbour Services case](../case-study/README.md), then repeat the exercise on an authorised process you know.

## 1. Understand the system you are using

An AI model transforms inputs into outputs using patterns learned during training. Inference is using that trained model on a new input. A conversation does not ordinarily retrain the underlying model. A product may save preferences, retrieve documents, or provide tools around it; those are additional parts of the system.

An assistant is the interface through which you ask for work. A workflow follows a defined sequence, such as reading a request, checking required fields, classifying it, and placing a draft in a review queue. An agent selects its next action from available tools based on what it observes. A language model can participate in either a workflow or an agent. Calling every automated process an agent obscures who controls the next step.

Consider Harbour's weekly report. Adding transaction amounts is a calculation. Deciding whether a mixed customer request belongs in billing or scheduling requires interpreting language. Deciding who may issue a refund is an authority question. Give calculation to code, use a model to suggest a classification, and enforce refund authority in application permissions. Asking a more capable model to do all three does not remove the need for these distinctions.

Language models process tokens, which are pieces of text rather than necessarily complete words. A context window limits what the model can use during one request. Long conversations and attachments consume that capacity; a product may retrieve or summarise some material rather than include it all. A convincing answer is not evidence that every source was read. Ask for a specific source ID and verify the relevant passage yourself.

The workflow/agent distinction is supported by [Anthropic's engineering guidance](https://www.anthropic.com/engineering/building-effective-agents). Our placement of arithmetic, classification, and authorisation is a design for this course's fictional business, to be tested against its requirements.

### A useful decision procedure

Start with the required output and the consequence of getting it wrong. If a formula or lookup fully specifies the answer, use that first. If the task predicts a numerical outcome from labelled historical data, investigate a predictive model and a simple baseline. If language interpretation is needed, try one bounded model call. Introduce an agent only when selecting the next tool is itself useful. Compare the additional setup and review work with the simpler process.

## 2. Work through an opportunity and a baseline

Suppose an owner says, "I want AI to run support." This is too broad to evaluate. A workable first version is: "Given one ticket, propose its category and whether a human must review it; save a draft without sending a response." It names an input, an output, an authority boundary, and a finish condition.

The ten fictional Harbour timings total 120 staff minutes. Their average is 12 minutes per case. Do not translate this directly into a savings claim. A real baseline needs a defined start and end, representative cases, and a record of rework. A single easy ticket processed in three minutes tells you little about the next week's mix.

Record a row for each case with case ID, task type, start/end, active staff minutes, waiting minutes, correction minutes, outcome, and reason for any exclusion. Keep interruptions distinguishable from work. Define "complete" before starting the timer: a draft without checking is not comparable with a fully reviewed manual response.

Rank opportunities using five questions: Is the task frequent? Is successful output observable? Is the necessary information available and authorised? Can mistakes be caught before affecting others? Is someone responsible for exceptions? The ranking is a discussion aid, not a mathematically objective score. A rare task with serious consequences may deserve a different process despite an impressive demo.

### Worked choice

Choose weekly report preparation for Harbour because the input files are bounded, numerical claims can be checked, and Maya already reviews the report. Leave refund execution outside the project. Success means the draft contains the correct reporting period, accepted totals, unresolved data problems, and evidence references; it does not mean every ticket is automatically resolved.

## 3. Studio, reflection, and evidence

### Engineering route

1. Run `node course/labs/reference.mjs report` from the repository root and read the input CSV separately.
2. Ask your approved assistant to calculate the same report using only the task inputs. Keep its original answer.
3. Compare its counts, exclusions, and totals with your manual check. If it gives the correct net amount for the wrong reason, mark the reasoning unsupported.
4. Write a one-page architecture decision allocating calculation, language interpretation, review, and final action to different components.
5. Repeat with ten examples from your chosen engineering process, or clearly label the Harbour pack as a simulation.

### Business-owner route

1. Draw the current process as receive, inspect, decide, act, and record. Name the person responsible for each step.
2. Time ten representative cases, or use the fictional baseline to practise the calculation.
3. List five possible improvements and rank them using the five questions above.
4. Choose one improvement. Write its allowed inputs, expected output, exclusions, review owner, and budget.
5. Ask a colleague to describe a failure you have missed. Add it to the project's future evaluation set.

### Check your understanding

If a report is generated instantly but takes 15 minutes to correct, it has not beaten a 12-minute manual process on active staff time. If an agent remembers a preference, that alone does not establish that its model was retrained. If a task can be completed by a deterministic calculation, a fluent explanation does not make a model the necessary execution engine.

Submit the baseline table, selected opportunity, rejected alternative, and task boundary. Pass this week's practical review when another person can determine whether a result is complete without asking what you meant.
