# Week 7: Business workflow automation

This week you will turn a useful model step into a process that can wait, fail, and resume. A workflow is complete when every input has a visible outcome and an accountable owner, including the inputs that did not succeed.

## 1. Represent work as durable states

Use explicit states such as received, validated, needs-review, approved, executing, completed, rejected, and failed. Persist the state before acknowledging that work has been accepted. A dashboard that shows only completed cases hides stuck work.

Attach a stable business-event ID to every run. Distinguish the original event from an execution attempt; a retry should not look like a new customer request. Save the proposed action as a versioned payload, including target, content, relevant source version, and expiry. Approval applies to that exact payload. A later edit requires a new decision.

Two people clicking Approve is a concurrency problem. A worker crashing after the external action but before recording completion is a distributed-systems problem. Checking a local "done" flag before sending is insufficient because the process can fail between the send and the flag update. A receiving API's idempotency key can make repeated identical requests return the same business effect. If the recipient cannot deduplicate, reconcile the uncertain outcome before retrying it.

The supplied simulator uses separate local workflow and simulated-provider databases. It intentionally crashes between the provider's committed effect and the workflow's completion record. A retry reuses the same action key and payload hash. This is a controlled demonstration, not a claim of exactly-once execution across arbitrary services. [SQLite's transaction reference](https://sqlite.org/lang_transaction.html) explains the local transaction boundary; it does not make a remote action part of that transaction.

## 2. Build a reviewable low-code flow

In n8n, start with a manual execution while developing. Use [Edit Fields](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.set/) to supply one fictional ticket and preserve its event ID. Add your model step and validate its output. Use an [If node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.if/) to route review-required items.

For an agent tool that can change an external system, n8n documents a [human-review connection](https://docs.n8n.io/advanced-ai/human-in-the-loop-tools/) that pauses execution for approval or denial. Configure the review destination to an internal test surface. Show the actual proposed tool arguments; a generic "continue?" prompt does not give a reviewer enough information.

Build the first flow as intake, validation, classification, draft preparation, review, and recording. There is no customer-send node in the initial lab. Add an error branch that records case ID, reason, attempt count, and responsible owner. A visual flow still needs a durable record and a deduplication design before it handles real events.

### Worked interruption

The provider accepts action A17. The worker crashes before marking A17 completed. On restart, the local record says approved, but the external effect may already exist. Retrying with a new action ID creates a duplicate. Retrying A17 with an identical payload against a provider that enforces idempotency returns the existing effect. Retrying A17 with changed content must be rejected, not silently treated as the approved action.

## 3. Studio and the recoverability gate

### Engineering route

1. Run `node course/labs/reference.mjs workflow` and inspect the reported interruption and resumed result.
2. Inspect the two database roles in the reference implementation. Explain the crash window in your own words.
3. Test duplicate delivery, denied approval, expired approval, changed payload, and restart after the simulated provider action.
4. Add a visible waiting state to your own workflow and a report of its oldest unresolved item.
5. Document the policy for ambiguous outcomes when a real recipient lacks idempotency support. Do not promise automatic recovery that your integration cannot provide.

### Business-owner route

1. Use the review prototype to practise approve, reject, edit, and resubmit on fictional cases.
2. Build the n8n flow described above in an approved test account, keeping output as a draft.
3. Define who checks the review queue, when a waiting item is overdue, and what happens if that person is absent.
4. Execute a complete request, a missing-field request, a rejection, and a repeated event.
5. Review the simulator's crash scenario with an engineer and write the staff procedure for an uncertain external action.

### Expected results

The same approved action should produce one simulated provider effect after a crash and retry. A denied or expired action produces none. An edit invalidates the previous approval. A failed item remains visible with a reason and owner; it does not disappear into an empty success response.

Submit the flow, state diagram, action/review record, failure matrix, and replay evidence. Pass the Week 7 gate when you can demonstrate validation, a human decision point, and recovery without a duplicate effect in the tested scenario. Use [the runbook template](../templates/runbook.md) to describe limits as well as successful recovery.
