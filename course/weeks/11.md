# Week 11: Grok Bot and platform comparison

This week you will delegate a bounded cloud task and compare systems on consistent evidence. The product called Grok Bot in this course is the one described in [Cursor's documentation](https://cursor.com/docs/grok-bot), not the separate Grok chat app. Verify account entitlement before the lab.

## 1. Define a Bot's job and authority

Grok Bot provides persistent Bots working with tools and a cloud computer. An important account boundary is that Bots belonging to the same account share files and sign-ins on that computer. Separate names and conversations do not establish separate security domains. The official [work guide](https://cursor.com/docs/grok-bot/work) describes this behaviour.

Create a Bot from the application's New action, give it the job "Harbour report preparer," and provide the [agent operating brief](../templates/agent-brief.md). Attach only fictional task inputs. Start with one Bot and one finished artifact before experimenting with handoffs.

Make the result explicit: a draft brief for 1-7 October, checked totals, source references, unresolved data, and proposed actions. Do not connect a real customer account for this exercise. If a plugin is enabled, inspect which identity and permissions it carries. An account-wide connection may be available beyond the one Bot you intended to use.

Consult [the security documentation](https://cursor.com/docs/grok-bot/security) to identify controls actually available on your plan. Some organisational enforcement and logging capabilities require Enterprise access. A personal instruction can communicate a rule but should not be represented as an administrator-enforced boundary when it is not one.

### Review the output as work, not conversation

Open the generated artifact, check the source IDs, reconcile the figures, and inspect tool activity. Distinguish a draft follow-up from a message already sent. Ask the Bot to state what it could not verify. If a website or sign-in requires your involvement, perform that authorised step yourself rather than giving credentials in the conversation.

## 2. Turn stable work into a tested routine

After a successful manual run, follow the [routines guide](https://cursor.com/help/grok-bot/routines) to create a test routine. Specify the source location, reporting window rule, timezone, output destination, and review owner. Test it once, inspect the result and run history, then pause it at the end of the exercise.

Recurring work needs a failure path. What happens when the input is missing, a connection expires, or the data has not refreshed? Require the routine to report that condition, not produce a plausible report from stale memory. Closing your application is not an adequate stop plan for work running on a cloud computer.

### Compare three complete systems

Run the common brief through OpenClaw, Hermes Agent, and Grok Bot. Keep the source files, output rubric, and reporting date the same. Use five cases: normal input, missing input, changed data, conflicting policy, and an embedded malicious instruction. Keep answer keys out of the supplied context.

Record correctness, review minutes, interventions, observed usage, elapsed time, permissions, recovery, and exportability. Label live runs, instructor replays, and unavailable features separately. Repeat cases when practical, since one run can hide variability.

Grok Bot's [model FAQ](https://cursor.com/help/grok-bot/models) says users cannot select or inspect the underlying model for an individual request. You therefore cannot force an identical model across all three platforms. Describe the results as a comparison of the complete systems you tested, and record the limitation.

## 3. Studio, scorecard, and the agent gate

### Engineering route

1. Configure one Bot with fictional inputs and a narrow operating brief.
2. Inspect artifact correctness and the available action history.
3. Create, test, and pause one routine. Verify the pause in the routine controls.
4. Run the five common cases across the three systems or clearly labelled instructor records.
5. Document where tool permissions, model visibility, logs, or exports differ. Do not fill missing measurements with estimates disguised as observations.

### Business-owner route

1. Define who receives and reviews the report, and what the Bot must do when a source is missing.
2. Run the brief and verify every proposed action is still a draft.
3. Review the routine configuration and stop procedure with the instructor.
4. Complete [the platform scorecard](../templates/platform-scorecard.md), including setup and maintenance effort.
5. Recommend a platform, a simpler workflow, or no deployment. Tie the choice to the business task rather than a general product ranking.

### Worked recommendation

Suppose one platform finishes faster but requires an administrator capability your subscription lacks. Another takes longer to set up but lets you enforce the required boundary. The measured winner for your organisation may be the second option, or a fixed workflow. A high average quality score cannot compensate for a mandatory permission failure.

Submit the reviewed artifact, tested and paused routine, five-case results for each platform, and a one-page recommendation. Pass the Week 11 gate when you can explain and demonstrate access boundaries and stopping work. Label any untested claim explicitly.
