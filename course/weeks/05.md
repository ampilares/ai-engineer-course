# Week 5: Model APIs and structured outputs

This week turns language output into an application interface. Start with recorded responses to test the surrounding software, then use a live model for quality evaluation if an approved account is available. A mock can test error handling; it cannot establish model accuracy.

## 1. Define the contract and validate twice

A model API takes a request and returns a response whose transport, completion status, and content must all be checked. An HTTP success does not necessarily mean the model produced a usable result. A response may be incomplete, refuse the request, or contain a well-formed but incorrect answer.

For ticket triage, define four fields: `id`, `category`, `needs_review`, and `reason`. Categories are billing, scheduling, technical, and unknown. The ID must match the submitted ticket. A review flag is a Boolean, not the strings "yes" or "false." A reason cites the request rather than claiming unsupported facts.

Schema validation checks shape, types, required fields, and allowed values. Business validation checks relationships: an unknown category must go to review; a refund cannot be treated as approved; the output ID must not switch to another customer. Semantic evaluation asks whether the category and review decision are actually correct. These are three different checks.

OpenAI's [structured-output documentation](https://developers.openai.com/api/docs/guides/structured-outputs) explains schema-constrained responses and exceptions such as refusal or incomplete output. The course's [optional live extraction example](../labs/live-extract.mjs) uses the Responses API, an explicit schema, and a model name supplied by the learner. It does not hard-code a supposedly permanent best model.

### A valid response can still be wrong

```json
{
  "id": "T09",
  "category": "billing",
  "needs_review": false,
  "reason": "The customer mentions an invoice."
}
```

All four fields have the right types. But T09 also asks to change a visit. The reference policy sends mixed intent to review. Passing the JSON parser is not sufficient for accepting this decision.

## 2. Handle failures and account for the whole operation

Classify failures before retrying. A temporary rate limit may justify a bounded delay. A wrong credential, disallowed action, invalid business field, or missing source needs a different response. Retrying a malformed request unchanged consumes time without addressing the problem. Retrying a side-effecting action after an ambiguous timeout can create duplicates unless the receiving system supports idempotency or reconciliation.

Record request ID, case ID, prompt version, visible model version, status, duration, token usage when exposed, and a review reason. Keep credentials and unnecessary personal content out of logs. Prefer a small structured failure record to dumping every raw request into permanent storage.

Cost per attempted call can make a poor system look inexpensive. If ten attempts cost AUD 0.40 but only eight complete successfully, model cost per success is AUD 0.05, before review and infrastructure. When pricing is token-based, estimate input tokens multiplied by the input rate plus output tokens multiplied by the output rate, using the provider's current units and separately accounting for cached tokens or tools where applicable. Verify the bill rather than assuming a chat subscription includes API use.

### Failure exercise

Use six cases: correct structured output, invalid category, missing ID, ID mismatch, refusal, and truncated output. A service should return a visible review or error outcome for each unusable case. Do not silently replace the failure with an empty successful record. A user needs to know which items have not been processed.

## 3. Studio, example calls, and evidence

### Engineering route

1. Inspect `triage.schema.json` and the validator in the reference lab.
2. Run `node course/labs/reference.mjs validate course/case-study/example-triage.json`.
3. Copy the response and change a category, Boolean, or ID. Verify rejection with a useful reason.
4. With approved API access, set `OPENAI_API_KEY` privately and `OPENAI_MODEL` to a model supporting the required schema feature, then run `node course/labs/live-extract.mjs T09`. The command sends only that fictional ticket.
5. Evaluate at least twenty cases, keeping fixtures separate from model inputs. If live access is unavailable, report interface results separately and leave model-quality claims unmeasured.

### Business-owner route

1. Use the [review prototype](../labs/review-prototype.html) to define category and review requirements on fictional tickets.
2. In your approved workflow builder, configure one model step to return the four fields. Use the supplied schema where the builder accepts JSON Schema.
3. Add field/type checks and a branch for unknown or review-required items.
4. Run the same six failure cases, inspect what staff see, and record the next responsible person.
5. Extend to the twenty practice cases, using a results table rather than relying on a few attractive examples.

### Expected reasoning

Missing customer information is not a licence to invent an ID. A Boolean-shaped answer is not proof that the classification is correct. Self-reported model confidence has no operational threshold until you establish what it predicts on labelled data.

Submit the schema, input/output examples, failure behaviour, twenty-case results, and cost per completed item. Explain which validations are automatic and which require a human. A missing live-model measurement is acceptable when labelled; claiming mock accuracy as model accuracy is not.
