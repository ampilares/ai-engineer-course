# Week 12: Evaluation, security, and governance

This week turns a set of demonstrations into a release decision. Define acceptable behaviour before looking at final results. A test suite is useful when it can reveal a reason not to release.

## 1. Build an evaluation that can disagree with you

Keep development cases separate from final assessment cases. Use development cases to change prompts, tools, and retrieval. Freeze the held-out set before final evaluation. If you inspect a held-out failure and tune to it, that case becomes development evidence; create fresh cases for the next independent assessment.

The course supplies twenty development and ten held-out cases for practice. They are public, so a formal assessment needs independently authored variants. Include common cases, ambiguous inputs, missing evidence, changed sources, access restrictions, and action boundaries. Use actual users' case distribution when assessing a real pilot, while testing rare consequential failures separately.

Measure end-to-end task success with a denominator. Separately count invalid outputs, wrong decisions, unsupported claims, interventions, and unauthorised actions. A single number can hide a system that answers easy cases beautifully and fails critical ones. Time out or cancelled cases belong in the attempted-case denominator unless the protocol predefines a different exclusion.

For subjective outputs, write a rubric with observable anchors. "Good report" is vague. "Every numerical claim reconciles; every policy claim cites an effective authorised passage; unresolved items remain visible" is reviewable. An LLM grader can scale some checks, but first compare its decisions with human labels. [OpenAI's evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices#llm-as-a-judge-and-model-graders) identifies limitations including response-order and verbosity bias.

## 2. Test the system's authority, not just its answers

A threat model identifies assets, actors, entry points, trust boundaries, and plausible failure effects. For Harbour, assets include customer records, policy content, credentials, and the ability to send messages. Entry points include tickets, retrieved pages, plugins, uploaded files, and saved skills.

Use the T08 fixture to test source content trying to redirect actions. Test whether the caller can change their own role, retrieve a manager-only document, alter a previously approved payload, or trigger an action after cancellation. The [OWASP prompt-injection material](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) is a primary security reference; your particular controls still need direct evidence.

Check logs and retained artifacts for unnecessary sensitive content. Revoking a source document is incomplete if it remains in a derived index, a memory entry, an exported file, or a trace accessible to the wrong person. Document the intended retention and deletion scope, then test it in the lab.

### Worked release decision

A candidate succeeds on 27 of 30 cases, but one failed case sends a message to an unauthorised recipient. Report 90% task success and the critical boundary failure. Do not average the latter away. The release decision is hold until the boundary is corrected and retested, even if the target success rate was 85%.

A different candidate completes 24 of 30 and sends the other six to review without unsafe actions. It may be suitable for an assisted pilot if the review workload is affordable. Define this operating mode honestly; it is not a fully autonomous process.

## 3. Studio and release evidence

### Engineering route

1. Run the reference evaluator on a saved prediction file. Inspect missing, duplicate, and extra IDs as well as incorrect labels.
2. Freeze your capstone's development/held-out split and versions.
3. Run boundary tests for access, tool scope, approvals, cancellation, stale sources, and log exposure.
4. Inspect a trace for the most consequential failure, change one component, and repeat affected regression cases.
5. Produce a release record stating pass, hold, or restricted pilot, with evidence for every mandatory condition.

### Business-owner route

1. Write acceptance criteria before inspecting the final outputs. Identify failures that always require a hold.
2. Independently grade a sample of results and compare with the system's automatic checks.
3. Review who can access data, which vendors process it, which permissions are needed, and how access is removed.
4. Name an owner for incident response, retention, complaints, and changes to the workflow.
5. Decide whether the system is acceptable for a bounded pilot and document the restrictions.

### Expected evidence

Submit the cases, rubric, version record, results with denominators, two reviewed traces, boundary-test evidence, and a release decision. Classroom thresholds are not guarantees of production safety. Larger or higher-consequence deployments require an evaluation designed for the actual stakes and operating conditions.

Use [the release record](../templates/release-record.md). If legal, regulatory, or contractual requirements affect the pilot, identify the appropriate organisational reviewer and record their decision rather than inventing a generic compliance claim.
