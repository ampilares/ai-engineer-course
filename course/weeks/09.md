# Week 9: Operate an assistant with OpenClaw

This week you will operate a dedicated assistant, inspect its authority, and recover it after a restart. Use only fictional inputs and a test messaging destination. Record the installed version and provider configuration; do not assume the documentation's current defaults match an older installation.

## 1. Establish a controlled lab

OpenClaw connects interaction channels to an agent through a gateway. The gateway, the model provider, and the tools can run in different places. Draw these locations before enabling tools. A locally running gateway may send a prompt to a hosted model; a search tool may send a query to another service.

Follow the official [getting-started guide](https://docs.openclaw.ai/start/getting-started) for your operating system and its current runtime requirements. In a dedicated lab environment, complete guided onboarding with an approved provider. Use the control interface for the first conversation before adding a messaging channel. The documented commands below inspect and open an installed gateway:

```bash
openclaw gateway status
openclaw dashboard
```

Check whether onboarding left the gateway in the foreground or installed a persistent service. A foreground run stops with its terminal; an installed service can continue after the dashboard closes. The [gateway CLI reference](https://docs.openclaw.ai/cli/gateway) documents status, lifecycle, and service operations. Choose a lifecycle deliberately and record the exact stop command for the installation you used.

Create a dedicated workspace containing only the agent inputs from Harbour. Exclude answer keys, evaluator labels, private policy passages, personal files, and credentials. Begin with read-only access and a reply in the test conversation as the output. If later work requires writing a report, add only a bounded output capability after proving the read-only configuration.

Consult [tool permissions](https://docs.openclaw.ai/gateway/security/tool-permissions) for the installed version. The guide distinguishes tool allow/deny rules from workspace access. Blocking a named write tool while leaving unrestricted shell access available does not establish a read-only boundary. Check all alternate ways the agent might access the same resource.

## 2. Connect, inspect, and test the boundary

Use the documented setup for one supported channel, such as a dedicated Telegram or Slack test integration. Configure authorised senders before accepting work. Restrict where the bot can respond. Avoid connecting a personal inbox merely to make the first demonstration more impressive.

Run the weekly brief from the common task specification. Record the received request, source IDs, observed tool calls, output, review duration, and unresolved items. Keep gateway health separate from task quality: a healthy process can still produce a wrong report.

Use the [security audit documentation](https://docs.openclaw.ai/cli/security) to inspect the deployment:

```bash
openclaw security audit
```

Read the findings and assess them against the lab's intended exposure. Do not apply automatic broad changes to an existing shared installation. The audit is a configuration check, not a certification that generated answers are safe or correct.

### Worked fault isolation

The dashboard loads, but messages do not arrive. Check channel authentication and sender routing before changing the model. Messages arrive, but a tool is denied. Check whether the denial is the intended permission boundary. Replies appear, but the total is wrong. Investigate source selection and calculation. These are different layers; reinstalling the entire product obscures the cause.

Restart after a completed report, then ask for a new report with changed input. Inspect which state persisted and which sources were reopened. Do not treat an old answer recalled from a session as a new calculation. Use [the sandboxing guide](https://docs.openclaw.ai/gateway/sandboxing) to understand which execution is isolated and which host-level capabilities remain available.

## 3. Studio, acceptance, and teardown

### Engineering route

1. Install or provision a dedicated OpenClaw lab from the current official instructions; record version, runtime, hosting location, and provider.
2. Copy only approved agent inputs to its workspace. Apply restrictive tool and file permissions.
3. Verify one control-interface chat, then configure one test channel and approved sender.
4. Request the common weekly brief. Verify AUD 6,300 net accepted transactions and the unresolved data rows independently.
5. Use a second controlled test identity to check sender rejection. Ask the authorised identity for a file outside the workspace and an unauthorised export; inspect the enforcement result.
6. Restart the gateway, rerun a changed-input case, and record whether it recalculates.
7. Stop any lab schedule or service and revoke the test channel credential when finished.

### Business-owner route

1. Obtain the prepared lab's hosting, provider, access, and support record from the instructor.
2. Complete an operating brief for Maya's daily or weekly report. Name the evidence and review owner.
3. Submit the report task and review every amount, source, and proposed action.
4. Observe the unauthorised-sender, out-of-scope request, and restart demonstrations. Record actual results, not claimed defaults.
5. Decide who would maintain this setup and respond if it stopped delivering reports.

### Acceptance and limitations

Submit the configuration inventory, a redacted action record, boundary-test results, restart evidence, and teardown record. A missing permission feature is an observed limitation; do not record a pass based on a prompt promise. If installation or account access is unavailable, use an instructor's recorded run and label your assessment as observed rather than hands-on. No live OpenClaw run is claimed by the creation of this course material.
