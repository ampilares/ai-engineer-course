# Week 8: Agents, tools, MCP, skills, and memory

This week you will give a model useful actions while keeping the application in charge of authority. Begin with two narrow tools, a short task, and a finite action budget. More tools create more choices and more possible failure paths.

## 1. Trace the agent loop

An agent receives a task and observations, chooses an action, calls a tool, observes its result, and decides whether to continue. The surrounding runtime must validate the tool name and arguments, check permissions and budgets, execute the call, and record what happened. A model's request to call a tool is not permission to execute it.

For Harbour, allow `search_policy` and `calculate_report`. Keep customer messaging and refunds unavailable. Stop after a fixed number of actions, elapsed time, or cost budget; also stop on cancellation or repeated failure. An agent that repeatedly searches the same missing document should return an unresolved question rather than continue indefinitely.

A tool contract needs an input schema, output schema, error states, authority requirements, and side-effect description. Make reads and writes distinct. A tool called `manage_customer` with arbitrary action text is harder to control than separate `read_ticket` and `prepare_draft` tools with narrow fields.

The [MCP introduction](https://modelcontextprotocol.io/docs/getting-started/intro) describes a host application, clients, and servers that expose capabilities. MCP supplies an integration protocol; it does not certify the trustworthiness of a server or automatically solve authorisation. Inspect what a server exposes and which credentials it uses. Refer to the [official tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) for the version used by your client, and record that version rather than assuming compatibility.

## 2. Distinguish context, state, memory, and skills

Context is the information available to a particular model request. Task state records the current process: which items are complete and which need review. Memory stores selected facts or preferences across sessions. A skill records a reusable procedure, sometimes with supporting scripts or templates. A source-of-truth business system remains separate from all four.

Suppose the agent remembers that a refund needs extra approval above AUD 500. P01-v2 changes the threshold to AUD 250. The memory is stale; retrieving the effective policy should override it. Stable preferences such as report format are different from changing business rules. Teach the agent to re-open current sources for amounts, statuses, and permissions.

Skills also need review. A saved procedure that includes a broad shell command or an unnecessary credential can repeat the same mistake every week. Version the procedure, inspect changes, and rerun evaluation cases after editing it. A shared skill's usefulness does not establish that its supporting code is safe to execute.

### Worked boundary attack

T08 asks the assistant to export customer files to an external URL. The text is source content from a ticket, not an instruction from the authorised operator. A robust lab blocks the attempted action because the export tool or network destination is unavailable. Reporting that the prompt said "do not export" is weaker evidence than a denied tool call recorded by the runtime.

The supplied [read-only MCP server example](../labs/mcp_server.py) uses the [official Python SDK](https://github.com/modelcontextprotocol/python-sdk). Its role is fixed by the application and it exposes only approved analyst policy search. Treat it as an instructional server; production identity and document access require integration with your own trusted authentication layer.

## 3. Studio and bounded execution

### Engineering route

1. Run `node course/labs/reference.mjs agent` and inspect the tool trace, including a denied export and a step-limit outcome. The planner is a deterministic fixture, not an LLM.
2. Replace the planner with your approved agent runtime while preserving the tool allowlist and validation.
3. In a separate Python environment, install the official MCP SDK, record its version, and launch `python course/labs/mcp_server.py` through your MCP client's local-server configuration. Use the absolute script path on your machine and the environment's Python executable.
4. Inspect the discovered tool list and call policy search. There should be no write, shell, customer-send, or role-switch tool.
5. Test a missing source, repeated tool failure, cancellation, an out-of-scope request, and the T08 instruction.

### Business-owner route

1. Complete the [agent operating brief](../templates/agent-brief.md): job, inputs, allowed actions, review owner, limits, and stop procedure.
2. Use a prepared runtime with the same two tools. Ask for one weekly brief and inspect its action history.
3. Ask for an action outside the brief and verify that the runtime prevents it.
4. Identify a preference that can be remembered and a business fact that must be rechecked.
5. Decide whether the task benefits from agent choices or works better as the Week 7 fixed workflow.

Submit a tool contract, permissions map, trace, stop demonstration, and a rejected request. Additional agents are an optional experiment: compare their coordination and cost with a single-agent baseline before adding them to the project.
