# Week 13: Deployment, economics, and adoption

This week prepares the system for a limited pilot. A useful deployment has an owner, a budget, observable failure, and a way back to the manual process. A successful installation is only one part of readiness.

## 1. Define the operating contract

Separate development, test, and pilot environments. Keep their credentials and data distinct. Record the deployed code, prompt, model identifier when visible, retrieval snapshot, tool configuration, and permission policy. A change to a provider's model routing may affect behaviour even when your own code is unchanged.

Choose a small set of signals: task success, unsupported-answer rate, intervention rate, oldest waiting item, end-to-end latency, and cost per completed case. Define what each measures and how often someone checks it. A server returning HTTP 200 does not establish that the business task succeeded.

A service-level indicator is a measured property. An objective is a target for that property over a stated window. For example, "at least 95% of eligible report requests produce a checked draft within ten minutes during the pilot" names a population, outcome, duration, and window. It is a proposed classroom target, not a universal requirement. [Google's SRE chapter](https://sre.google/sre-book/service-level-objectives/) provides the underlying distinction.

Set stop conditions before rollout: an unauthorised action, a privacy boundary failure, spend beyond the agreed cap, or repeated missed deadlines. Stopping new work is different from cancelling work already in progress. Record how to inspect pending actions, revoke tool access, preserve evidence, and return users to a manual queue.

### Deployment checklist as an operating exercise

Confirm secrets are outside the repository, logs are appropriate, backups can be restored, and dependencies are recorded. Rehearse recovery with fictional data. A backup that has never been restored is unverified. Ask a second person to follow the runbook without your help; their questions reveal missing operational knowledge.

## 2. Calculate value and plan adoption

Use the [fictional baseline](../case-study/baseline.json) to practise, then replace it with authorised measurements for a real decision. Manual staff time averages 12 minutes and pilot staff time averages 6.5, including review. At 200 cases per month and AUD 60 per hour, the released capacity value is:

```text
200 × (12 − 6.5) / 60 × 60 = AUD 1,100 per month
1,100 − 120 tools − 180 maintenance = AUD 800 net capacity value
1,200 implementation / 800 = 1.5 months theoretical payback
```

Released capacity is not automatically cash savings. Staff may use the time on other work, or the organisation may not have enough demand to benefit. Revenue improvement needs separate evidence. Do not count review time both in pilot staff minutes and again as an operating expense.

At 100 cases, net capacity value is AUD 250 with the same fixed costs. At 50 cases, it is negative AUD 25; a positive payback period is undefined. Test low, expected, and high volumes and explain which costs actually vary. This calculation is an original teaching example, not a forecast for a real organisation.

Adoption is a process change. Show staff what the system does, what it cannot do, what needs checking, and how to report a problem. Do not ask users to trust an unexplained score. Give them source evidence and a correction path. Track whether people actually use the output and whether it changes a decision.

## 3. Studio and pilot readiness

### Engineering route

1. Deploy your candidate to a controlled environment or provide a reproducible local pilot package.
2. Record versions and configuration, then run a smoke test and the relevant regression cases.
3. Add monitoring for unresolved work, failures, duration, and cost. Test an alert by causing a controlled failure.
4. Restore from a known snapshot or roll back one change. Verify the queue and external-action state afterwards.
5. Give the runbook to another operator and record the time and questions required to recover.

### Business-owner route

1. Complete the [pilot charter](../templates/pilot-charter.md) with scope, users, owner, review duty, budget, and stop conditions.
2. Calculate value at three volumes using measured or explicitly fictional inputs.
3. Train one user with a normal case and a misleading result. Observe whether they check the intended evidence.
4. Test the manual fallback and the process for reporting errors.
5. Agree when the pilot will be reviewed and who may decide to expand it.

### Deliverable

Submit the operating contract, tested runbook, cost model, training note, and pilot charter. Do not describe the candidate as ready if no one owns its failures. A restricted pilot or a decision to stop can be a successful result when supported by evidence.
