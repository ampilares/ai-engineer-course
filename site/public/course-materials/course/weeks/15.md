# Week 15: Capstone pilot and improvement

This week collects evidence from bounded use. Run with a small authorised group, or label the work as a simulation. The objective is to learn whether the system improves the agreed process and to fix the most consequential observed failure.

## 1. Run a pilot that produces usable evidence

Before the first case, confirm the operating mode, participants, reporting window, budget, review duty, and stop conditions. Keep a record of every attempted case, including cancellations and incomplete runs. Save original outputs before corrections so you can distinguish model performance from final staff-assisted performance.

For each case record input reference, configuration version, start/end, active staff minutes, waiting time, review outcome, correction type, final success, and cost. A run that finishes quickly but spends a day waiting for an unassigned reviewer has poor end-to-end service. Separate those two timings.

Use the same completion definition as the manual baseline. If the baseline includes checking and correction, the pilot must include them too. Record changes in case mix: a pilot with only easy cases cannot establish improvement for the whole workload.

### Worked pilot result

Twelve cases enter the system. Nine complete correctly without correction, two complete after human correction, and one remains unresolved. Report first-pass success as 9/12, final completed success as 11/12, and unresolved work as 1/12. Do not report 9/9 by excluding the cases that needed help. Explain what the human corrections changed.

If all twelve cases came from the fictional pack, describe the result as a classroom simulation. It can demonstrate process behaviour but not staff adoption or real savings. If users are real, record their consent and authorised data use through the organisation's normal process.

## 2. Diagnose failures before changing the system

Classify the failure by stage: input quality, retrieval, model interpretation, schema, business validation, tool execution, review, or operations. An incorrect current policy may be a retrieval filter problem, not a weak model. A duplicate external action may be an idempotency problem, not a bad prompt.

Choose the most consequential failure using severity and exposure, not the easiest cosmetic issue. Preserve a reproduction case. State a hypothesis, make a targeted change, and rerun the affected regression set. If you change several components, say that the cause of improvement is not isolated.

### Worked improvement

The report includes the draft automatic-refund proposal. The trace shows retrieval passed it to the generator. Fix the document-status filter, add a regression case containing a highly relevant draft, and verify that the approved effective policy is selected. Changing the report's tone does not address the source-selection defect.

Another failure occurs after a tool times out. The operator cannot tell whether the action was performed. The fix may require an external receipt lookup or a manual reconciliation state. Adding more retries without understanding the action's idempotency can make the incident worse.

Keep held-out discipline. If final assessment reveals a failure and you inspect it to repair the system, that example is now part of development. After the fix, rerun it as regression evidence and use new independent cases for any renewed final-quality claim.

## 3. Studio and pilot review

### Engineering route

1. Run the bounded pilot with instrumentation and a visible unresolved-work queue.
2. Review traces for at least one success, one corrected result, and one failed or deliberately injected failure.
3. Fix the highest-priority defect and preserve its regression case.
4. Compare before and after on the same development cases, recording versions and any confounding changes.
5. Rehearse rollback or stopping new work, then verify the state of already-started actions.

### Business-owner route

1. Observe users completing the actual review task. Ask where they felt uncertain or needed to leave the workflow.
2. Record review and correction time, not only generated-output time.
3. Check whether users relied on unsupported claims or ignored unresolved items.
4. Agree a targeted improvement with the implementation owner and retest with staff.
5. Update the adoption recommendation and cost sensitivity using the observed workload.

### Required submission

Submit the pilot case log, before/after results, feedback notes, one diagnosed failure, the fix and regression evidence, and an updated decision record. A pilot that recommends stopping can earn full credit if it uses a working system and sound evidence. Positive ROI is not a grading requirement; honest measurement and a defensible decision are.

Before moving to handover, ensure that unresolved cases have owners, the pilot has stayed within its authorised scope, and the final evaluation claims are independent of the development examples used to tune the system.
