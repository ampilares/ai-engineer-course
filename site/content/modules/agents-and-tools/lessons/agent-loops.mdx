One tool call handles one bounded operation. An **agent** closes a loop: the model selects an action, calls a tool, observes the result, updates its working state, and continues until it reaches a terminal condition. This loop enables the system to complete variable multi-step work. It also creates additional risk because model decisions can influence external state repeatedly. ## What the loop adds and what it costs

The bounded run verifies state before acting, recognizes a refund threshold above €50, pauses for approval, and then performs the authorized action. The unbounded run skips verification, retries without a progress rule, changes its approach without evidence, and quickly produces a consequential error.

Learn these recurring failure modes:

- **No state verification**: acting on assumptions instead of checking (`issue_refund` before `get_order`).
- **Unbounded retries**: errors trigger "creative" variations; creativity plus side effects equals damage.
- **No loop budget**: an agent that cannot reach its goal may continue consuming tokens and calling tools. Every loop needs maximum iterations, wall-clock time, and cost or usage limits.
- **Error-cascade drift**: one misread result poisons every subsequent step's reasoning; the agent ends up solving the wrong problem diligently.
- **Non-idempotent retries**: Module 3's double-charge problem, now automated.

## The three walls around every production agent

1. **Least privilege**: the agent gets exactly the tools this task needs, with the narrowest scopes. A summarization agent has no `send_email`. Most attacks and accidents die here, *without being detected*, because the capability simply doesn't exist.
2. **Approval gates**: consequential actions (money, deletion, external communication, anything irreversible) pause the loop for a human. The unit of review is the *action*, not the plan: humans approve `refund €89 on ORD-4821`, not "I intend to help the customer."
3. **Budgets**: iterations, tokens, cost, and wall-clock per task. Hitting a budget is a *routable outcome* (escalate to human), not an error.

State lives outside the loop too: a durable record of every step, tool call, and result, so a crashed agent can resume (or be audited) rather than restart with amnesia. That's Module 3's database habit joining Module 10.

## State makes the loop recoverable

An agent run is a state machine, even when a framework hides it. Persist the objective, messages or compact working state, proposed and completed actions, tool results, approvals, budget consumed, and terminal status. After a crash, resume from the last committed step; do not replay a side effect just because the conversation was reconstructed.

Separate **working context** from durable business state. The prompt may contain a summary of progress, but the database remains authoritative for orders, approvals, and completed actions. Memory retrieval is another tool with relevance, privacy, and staleness failure modes, not an infallible extension of the model.

Loops need terminal conditions for success, safe refusal, human escalation, budget exhaustion, repeated failure, and cancellation. Detect repeated identical calls and no-progress cycles. A planning step can help on long tasks, but plans are hypotheses to revise after tool evidence, not guarantees.
