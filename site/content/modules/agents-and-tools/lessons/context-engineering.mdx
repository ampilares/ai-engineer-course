An agent that runs for fifty steps, a chat that spans three weeks, a workflow that processes a 400-page contract: all collide with the same wall: **the context window is finite, and everything the model should know must fit in it, every single call.** Deciding *what earns those tokens* is context engineering, and it has quietly become one of the highest-leverage skills in applied AI.

## The budget mindset

Treat the context window as a budget to allocate, not a bucket to fill. A long-running assistant's context competes among: system instructions and tool schemas (fixed overhead), conversation/step history (grows without bound), retrieved knowledge (Module 9), and working state (what's been decided, what's pending). Overspend and you hit three separate walls: hard truncation (silent loss), *lost-in-the-middle* degradation (Module 7: big contexts get skimmed, not read), and cost/latency (every token, every call).

The discipline: **spend tokens proportional to relevance, not recency of arrival.** Most raw history is low-value; the few load-bearing facts are precious.

## Memory patterns that work

- **Rolling summarization:** When history exceeds a threshold, compress the oldest span into a concise summary and keep recent turns verbatim. Summaries can lose detail irreversibly, so preserve exact facts and commitments such as `order ORD-4821; refund €89 approved; contact by email` instead of writing "we discussed an order."
- **Structured state instead of transcript**: for agents especially: maintain an explicit scratchpad (`goal, facts_established, actions_taken, pending`) updated each step, and feed *that* forward rather than the full step-by-step history. Fifty steps of tool output compress into twenty lines of state. This is Module 3's "durable state" habit meeting the context window.
- **Memory as retrieval:** Store durable facts, preferences, past decisions, and entity knowledge outside the prompt in an appropriate database or retrieval system. Retrieve only what is relevant and authorized for the current request. Nothing persists in a context window between sessions; durable storage and controlled retrieval create the memory behavior.
- **Fixed-prefix hygiene**: keep the stable parts (instructions, schemas, examples) identical and *first*, so prompt caching (Module 8) makes your fixed overhead nearly free.

## What survives summarization: a design decision

Every compression step determines what the working context may no longer contain. Preserve commitments and constraints, such as a promised refund date. Preserve identifiers exactly because paraphrasing can corrupt order numbers or email addresses. Remove redundant retrieved chunks, verbose tool payloads, and conversational filler. Before acting on a consequential fact from a summary, verify it against the system of record because summaries are model-generated output.
