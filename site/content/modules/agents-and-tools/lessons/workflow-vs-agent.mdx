The most expensive design mistake in applied AI right now is building an agent where a workflow belongs. The judgment call is simple to state and career-defining to apply: **who controls the flow?**

## Two architectures

- **Workflow:** *your code* controls the sequence; models fill in judgment-shaped steps. `receive email → model: classify → if billing: model: extract fields → validate → if confident: create ticket; else: human`. Every arrow is deterministic; every model call has one bounded job.
- **Agent:** *the model* controls the sequence: it decides what to do next, step by step, using tools, until done.

The engineering trade is stark. Workflows are predictable, testable step-by-step, debuggable ("step 3 failed"), cheap (each call minimal), and reliable in the way multiplication punishes agents: a 10-step agent at 95% per-step reliability finishes right ~60% of the time; a workflow chains deterministic steps and spends model reliability only where it must.

**Use an agent only when the path genuinely cannot be enumerated** (open-ended research, debugging, "figure out why this invoice doesn't reconcile") tasks where which step comes next depends on what the last step revealed.

## MCP: the USB port for tools

The Model Context Protocol (MCP) standardizes how AI applications discover and call external tools. Instead of writing bespoke integration code for every application and system pair, a system can expose an **MCP server** that describes its tools, resources, and schemas. An MCP-capable client can then connect to authorized file, database, or ticketing capabilities through the same protocol.

The strategic point for an engineer: MCP changes *where integrations live* (a standard interface, reusable across apps), not *what the model can do*. Every lesson in this module (least privilege, approval gates, budgets) applies identically to MCP tools. A standardized connector to your production database is a standardized blast radius; scope it accordingly.

## Use a spectrum, not a binary

Useful architectures range from deterministic pipelines, to workflows with one model decision, to model-routed graphs, to open loops. Most production systems belong in the middle. Encode known order, retries, approvals, and compensation in a workflow engine; use a model only for the step whose input cannot be enumerated cleanly.

MCP standardizes how clients discover and invoke tools, prompts, and resources. It does not decide whether a server is trustworthy. Review server ownership, authentication, capability scope, data retention, network access, version compatibility, and user consent. Pin or test interface versions and expose the smallest server set required for a task. A newly installed server changes the agent’s attack surface.

Architecture should also include an exit. If a model decision repeatedly fails, the workflow needs a deterministic fallback, human queue, or safe cancellation path. Compensation, undoing or counteracting earlier actions, must be designed for multi-step writes that cannot be transactional.

## Guided design: choose the least variable architecture

Model one business task in three ways: deterministic workflow, workflow with a single LLM decision, and bounded agent. For each, estimate task coverage, failure modes, latency, cost, auditability, and required approvals. Select the least variable design that handles the real exception rate.

If you use MCP, connect one local or sandboxed server and document its capabilities and trust boundary. Demonstrate denial of an out-of-scope call and behavior when the server schema changes. Submit the architecture decision record, sequence diagram, and test evidence.
