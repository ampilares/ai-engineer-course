### Engineering route

1. Inspect `triage.schema.json` and the validator in the reference lab.
2. Run `node course/labs/reference.mjs validate course/case-study/example-triage.json`.
3. Copy the response and change a category, Boolean, or ID. Verify rejection with a useful reason.
4. With approved API access, set `OPENAI_API_KEY` privately and `OPENAI_MODEL` to a model supporting the required schema feature, then run `node course/labs/live-extract.mjs T09`. The command sends only that fictional ticket.
5. Evaluate at least twenty cases, keeping fixtures separate from model inputs. If live access is unavailable, report interface results separately and leave model-quality claims unmeasured.

### Business-owner route

1. Use the [review prototype](/course-materials/course/labs/review-prototype.html) to define category and review requirements on fictional tickets.
2. In your approved workflow builder, configure one model step to return the four fields. Use the supplied schema where the builder accepts JSON Schema.
3. Add field/type checks and a branch for unknown or review-required items.
4. Run the same six failure cases, inspect what staff see, and record the next responsible person.
5. Extend to the twenty practice cases, using a results table rather than relying on a few attractive examples.

### Expected reasoning

Missing customer information is not a licence to invent an ID. A Boolean-shaped answer is not proof that the classification is correct. Self-reported model confidence has no operational threshold until you establish what it predicts on labelled data.
