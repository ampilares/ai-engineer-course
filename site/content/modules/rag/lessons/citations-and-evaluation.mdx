Retrieval found the chunks; now generation must be **held to them**. The difference between a trustworthy knowledge assistant and a liability is three disciplines: grounding instructions, an abstention path, and separated evaluation.

## Grounded generation: the prompt contract

```text
Answer the question using ONLY the provided sources.
After each claim, cite its source like [1].
If the sources do not contain the answer, say exactly:
"I don't have enough information in the knowledge base to answer this."
Do not use outside knowledge, even when confident.

Sources:
[1] (Refund Policy §2, updated 2026-03) "Refunds are available within 30 days…"
[2] (Shipping FAQ) "Standard delivery takes 3–5 business days…"

Question: {question}
```

Three design choices carry the weight:

- **Citations per claim** make answers *checkable*: by users, by reviewers, and by your evals. An uncitable sentence is a red flag by construction.
- **The abstention path is engineered, not assumed.** A model can generate a refusal, but it will not do so reliably without a defined policy, evidence threshold, and measurable output. Use an exact, detectable response for insufficient evidence and treat correct abstention as a successful outcome. A RAG system that never abstains should be tested aggressively for unsupported answers.
- **"Only the provided sources"** suppresses the model's parametric guesses: imperfectly. Enforcement comes from evaluation, below.

## Evaluate the stages separately

A RAG system fails in two independent places, and one end-to-end score cannot tell you which. So build **two eval sets**:

**1. Retrieval evals**: questions with hand-labeled relevant chunks. Metrics:
- **Recall@k**: is a relevant chunk in the top k? (If not, generation never had a chance.)
- **MRR/precision@k**: how high and how clean is the ranking?

Cheap to run (no generation!), so iterate chunking, hybrid weights, and rerankers against them freely.

**2. Generation evaluations:** Given the correct retrieved chunks, judge whether the answer is faithful to the sources, cites its claims, and abstains when the sources are silent. Include a meaningful share of unanswerable questions and report the abstention and unsupported-claim rates.

The debugging flowchart falls out automatically: wrong answer → check what was retrieved → *relevant chunks present?* No → fix retrieval (chunking, hybrid, reranking). Yes → fix generation (grounding prompt, model choice).

## Verify claims, not decorative footnotes

A citation is useful only if it identifies a stable source location and supports the adjacent claim. Ask the generator to produce claim-level source IDs from the supplied context, then validate that every cited ID was actually retrieved. For high-stakes workflows, split the answer into atomic claims and grade entailment against the cited passage. A source that is relevant to the topic may still fail to support the exact number, date, or condition stated.

Separate failures into retrieval miss, context selection, unsupported generation, citation mismatch, and appropriate abstention. This taxonomy tells you what to change. End-to-end “answer quality” alone can hide a generator that guesses correctly despite failed retrieval or a retriever that finds the evidence while generation ignores it.

Evaluate permission isolation and freshness as correctness properties. Include queries where an old document conflicts with the current version and users with different access should receive different evidence.
