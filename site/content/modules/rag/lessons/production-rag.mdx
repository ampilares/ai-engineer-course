The RAG you've built so far answers questions correctly in a lab. Production adds the constraints that actually sink knowledge assistants: documents change hourly, different users may see different documents, and the corpus grows 100×. This lesson covers the three disciplines (freshness, permissions, scale) that separate a demo index from a system of record.

## Freshness: the index is a cache, and caches go stale

Your vector index is a *derived copy* of the source documents, and every derived copy drifts. The policy PDF gets revised; the old chunks keep answering. Production RAG treats ingestion as a **continuous pipeline** (Module 4's habits, pointed at retrieval):

- **Detect changes**: webhooks or modified-since polling on sources, not monthly re-crawls. Track per-document `version` and `ingested_at`.
- **Upsert and delete, not append:** Changed documents replace their old chunks. Stable chunk IDs derived from the source and position make replacement practical. Deleted documents must also delete their chunks. An append-only index can continue serving retracted policies and create a compliance incident.
- **Surface freshness to the model and user**: chunk metadata carries source and effective dates; retrieval can prefer or filter by them; citations expose the version and effective date used for the answer.
- **Alert on staleness**: `now − max(ingested_at)` per source is a metric with a threshold (Module 14). Silent pipeline death is the most common way RAG rots.

## Permissions: filter at retrieval, enforce at the index

Module 9 stated the rule (*unauthorized chunks never enter the context*) and Module 15 explained why prompts can't enforce it. Production mechanics:

- **Access tags on every chunk at ingestion** (inherited from the source system's ACLs), and **mandatory filters at query time**: the retrieval call itself carries the user's permissions; unauthorized chunks are never even scored.
- **Sync permission *changes***: revoking someone's access to a folder must reflect in query filters promptly; permission drift is quieter than document drift and more dangerous.
- **Multi-tenant = hard isolation.** Separate collections (or provably mandatory tenant filters) per customer. A shared index with an optional filter is one forgotten `WHERE` clause away from a cross-customer breach: make the wrong query *impossible*, not just avoided.

## Scale: what actually changes at 100×

Scale changes several implementation choices. Exact search may give way to **approximate nearest-neighbor** indexes, making recall and latency a tunable trade-off that retrieval evaluations must verify. Ingestion often becomes a queued, monitored pipeline with a dead-letter queue. An embedding-model upgrade becomes a migration because vectors from different models are not directly comparable; build a separate index, evaluate it, then cut over with rollback available. Retrieval latency also becomes part of the end-to-end p95 budget because it precedes every generated answer.

The core concepts remain stable: chunking, hybrid search, metadata filtering, and stage-level evaluation still apply. Scale changes the operational design around them. Production RAG therefore depends as much on pipelines, access control, monitoring, and deployment discipline as it does on retrieval algorithms.
