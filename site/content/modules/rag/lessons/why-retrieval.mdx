Your model has never read your company's refund policy, doesn't know yesterday's outage report, and must never see another customer's contract. Yet users will ask about all three. **Retrieval-augmented generation (RAG)** is the standard answer: find the relevant documents at question time, put them in the context window, and instruct the model to answer *from them*, with citations.

## The core insight: separate knowledge from language skill

Module 7 gave you the diagnosis tools. The model's weights hold *language competence* plus a frozen, fuzzy snapshot of public knowledge. Your actual knowledge (private, precise, constantly changing) should live where knowledge belongs: in documents and databases, **outside** the model. RAG connects the two per request:

```text
question → [retrieve: find top-k relevant chunks] → [augment: build prompt
           with chunks + rules] → [generate: answer only from chunks, cite]
```

Why this beats the alternatives for knowledge problems:

- **vs. prompting alone**: the facts simply aren't in the weights; no phrasing conjures them.
- **vs. stuffing everything in context**: 10,000 pages don't fit; what fits gets the "lost in the middle" treatment; and you'd pay for every token, every request.
- **vs. fine-tuning**: bakes in a snapshot (stale tomorrow), can't cite sources, can't do per-user access control, and doesn't reliably add *facts* anyway (it shapes behavior more than knowledge).

And the operational bonuses: update the knowledge by updating documents (no retraining); enforce **permissions at retrieval time** (only search what this user may see); and get **verifiability**: an answer with citations can be checked; a fluent paragraph cannot.

## What RAG actually buys you: an honest ledger

**Credits:** current knowledge; private knowledge; citations; access control; hallucination *reduction* (the model paraphrases provided text instead of free-associating).

**Debits:** a whole new failure surface. If retrieval returns the wrong chunks, the model now confidently answers from irrelevant text: garbage in, eloquent garbage out. The system is only as good as its *worst-retrieved* context, which is why the next two lessons are about making retrieval good and *measuring* it separately.

## RAG is a data pipeline with a generation step

The offline path discovers sources, parses them, preserves structure, attaches metadata, chunks content, embeds it, and publishes a versioned index. The online path authenticates the user, interprets the query, applies permission and freshness filters, retrieves and reranks candidates, builds context, generates an answer, and verifies citations. Either path can fail independently.

RAG is appropriate when answers depend on a bounded, changing corpus and users benefit from evidence. It is not the default for simple database lookups, calculations, actions, or knowledge already stable in the model. Use SQL or an API for exact structured facts; use a tool for computation; fine-tune when the gap is repeated behavior rather than changing knowledge.

Define the answerability boundary. Which sources are authoritative? How fresh must they be? What happens when sources disagree? Which users can retrieve each document? If permission filtering occurs after retrieval, restricted text may already be in the model context.

## Guided design: retrieval decision record

Choose three candidate questions from your domain. For each, decide between model-only response, SQL/API tool, RAG, or human routing. Defend the choice using freshness, exactness, evidence, permissions, latency, and maintenance.

For the RAG candidate, draw offline and online paths and specify source ownership, update frequency, deletion behavior, access-control metadata, abstention response, and stage-level metrics. The design passes when a deleted or permission-revoked document can be proven absent from retrieval, not merely hidden in the interface.
