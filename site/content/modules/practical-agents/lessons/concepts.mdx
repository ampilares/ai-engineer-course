This week you will give a model useful actions while keeping the application in charge of authority. Begin with two narrow tools, a short task, and a finite action budget. More tools create more choices and more possible failure paths.

An agent receives a task and observations, chooses an action, calls a tool, observes its result, and decides whether to continue. The surrounding runtime must validate the tool name and arguments, check permissions and budgets, execute the call, and record what happened. A model's request to call a tool is not permission to execute it.

For Harbour, allow `search_policy` and `calculate_report`. Keep customer messaging and refunds unavailable. Stop after a fixed number of actions, elapsed time, or cost budget; also stop on cancellation or repeated failure. An agent that repeatedly searches the same missing document should return an unresolved question rather than continue indefinitely.

A tool contract needs an input schema, output schema, error states, authority requirements, and side-effect description. Make reads and writes distinct. A tool called `manage_customer` with arbitrary action text is harder to control than separate `read_ticket` and `prepare_draft` tools with narrow fields.

The [MCP introduction](https://modelcontextprotocol.io/docs/getting-started/intro) describes a host application, clients, and servers that expose capabilities. MCP supplies an integration protocol; it does not certify the trustworthiness of a server or automatically solve authorisation. Inspect what a server exposes and which credentials it uses. Refer to the [official tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) for the version used by your client, and record that version rather than assuming compatibility.
