Every AI system is a data system wearing a trench coat. Before a model can extract, classify, or answer anything, the data has to arrive, be validated, and be stored somewhere queryable, and after the model runs, its outputs need the same treatment.

## Files: where data arrives

You'll meet three formats constantly:

- **JSON**: the native tongue of APIs and model outputs. Nested, flexible, and easy to break: a missing key is a runtime error waiting to happen.
- **CSV**: the native tongue of spreadsheets and exports. Deceptively simple: encodings, delimiters inside quotes, and type-less columns cause endless grief.
- **Parquet**: columnar and compressed; what you graduate to when CSVs get big.

The engineering habit that matters: **validate at the boundary**. The moment data enters your system, check it against what you expect: don't let malformed records travel deep into your pipeline before exploding.

## SQL: a compact language with lasting value

Relational databases store data in typed tables and answer questions with SQL. SQLite (a full database in a single file, no server) is perfect for learning and for a surprising share of production workloads.

```sql
CREATE TABLE readings (
    id INTEGER PRIMARY KEY,
    city TEXT NOT NULL,
    temp_c REAL NOT NULL,
    recorded_at TEXT NOT NULL
);

-- The questions you'll ask forever:
SELECT city, AVG(temp_c) AS avg_temp
FROM readings
WHERE recorded_at >= '2026-07-01'
GROUP BY city
HAVING AVG(temp_c) > 20
ORDER BY avg_temp DESC
LIMIT 5;
```

Read that query aloud: *from the readings since July, group by city, keep cities averaging over 20°, sort, top five.* SQL is declarative: you state what you want; the database figures out how.

## The one security rule of SQL

Never build queries by pasting strings together:

```python
# NEVER: one malicious city name and your table is gone
cursor.execute(f"SELECT * FROM readings WHERE city = '{city}'")

# ALWAYS: parameterized: data stays data
cursor.execute("SELECT * FROM readings WHERE city = ?", (city,))
```

This is **SQL injection**, and it has a sibling you'll meet in the security module: *prompt* injection, where untrusted text gets concatenated into model instructions. Same disease, different host, and the parameterized-query mindset (keep data and instructions separate) is the beginning of the cure for both.

## Databases as system memory

In AI systems, the database isn't just for source data. You'll use it for **state** (which items are processed, pending, failed), **audit** (what did the model output, when, at what cost), and **evaluation** (inputs, expected outputs, actual outputs). When Module 13 builds durable workflows, "the workflow survives a crash" will mean exactly "its state lives in a database, not in a variable."

## Model the lifecycle, not just the object

A useful schema records how work changes over time. For an AI extraction job, a single `documents` table is rarely enough. Separate the immutable input, processing attempts, validated result, and review decision. That lets you answer: Which source produced this result? Which model and prompt version ran? Was the item retried? Who approved it? Can we reproduce it?

Use database constraints as executable rules. `NOT NULL`, `UNIQUE`, foreign keys, and `CHECK` constraints reject impossible states regardless of which code path writes the row. Wrap related writes in a transaction so they either all commit or none do. Add indexes for actual access patterns, such as `(status, created_at)` for a worker queue, after measuring queries, not by indexing every column.

For changing data, prefer additive migrations and explicit schema versions. A model output is not “just JSON”: store the raw response for audit, but also parse the fields you query into typed columns. Track provenance with source ID, source timestamp, ingestion timestamp, and a content hash.
