You've built a reliable workflow. Now comes the part that determines whether it survives contact with the organization: the **pilot**, the **numbers**, and the **rollout**. AI projects rarely die of bad models; they die of unmeasured value and unmanaged change.

## Pilot like a scientist

Run the automation **in parallel** with the manual process on a slice of real volume (one team, one region, two weeks). Parallel running de-risks everything: the manual process still catches what automation misses, and you harvest a paired comparison on identical traffic.

Define success criteria *before* the pilot: "≥95% of auto-processed items correct, cycle time under 10 minutes, reviewers report net time savings." Pre-registered criteria prevent the two classic endings: calling a failure a success because sunk cost, or calling a success a failure because one anecdote.

## The ROI arithmetic

Keep it simple enough for a CFO to redo on a napkin:

```text
BEFORE (measured baseline):        900 invoices/mo × 11 min = 165 h ≈ €5,775/mo
                                   error rate 2.1% → ~19 rework cases
AFTER (pilot measurements):        automation handles 78% clean
                                   human review 22% × 3 min = 9.9 h
                                   error rate 0.5% → ~4 cases
COSTS:                             API ~€140/mo + hosting €30 + maintenance ~0.1 FTE
NET:                               ≈ €4,300/mo saved + 3 days faster cycle time
```

Two honesty rules. Count **all** the costs: API tokens, hosting, the review queue's human minutes, and the engineering time to maintain it. And report the **failure numbers** alongside the wins: the 22% review rate and what those items look like. Stakeholders who hear honest numbers trust your next proposal; stakeholders who catch inflated ones don't fund it.

## Change management, compressed

- **The operators decide adoption.** Involve them from mapping (they did the analysis with you), give them the override, and make the tool visibly *theirs*: "the assistant the AP team designed," not "the bot management installed."
- **Fear is rational; address it with roles, not slogans**: the job shifts from typing to reviewing; say so explicitly, and mean it.
- **Keep the manual path executable.** When (not if) the automation has a bad day (provider outage, format change upstream) the team must be able to fall back without drama. An automation with no manual fallback is a single point of failure you *added*.

## Measure realized value, not theoretical capacity

Automation value depends on eligible volume, adoption, successful completion, and whether saved time is actually redeployed. Multiply those rates instead of assuming every case uses the system perfectly. Include review time, exception handling, support, integration maintenance, model calls, and incident risk. Run sensitivity analysis for volume, quality, and adoption rather than presenting one precise forecast.

Choose a pilot design that supports a causal claim. A phased rollout, randomized eligible cases, or matched before/after cohort is stronger than comparing one good week with an old average. Track protected metrics, error severity, customer complaints, employee workload, and escalation, not only speed. Define stop conditions before the pilot begins.

Rollout needs ownership. Name the process owner, technical owner, reviewer capacity, training plan, feedback channel, and decision forum. A pilot that succeeds only while its builder watches every run has not proved operability.

## Guided build: pilot decision pack

Create a baseline from at least 30 cases and design a limited pilot. Report eligibility, adoption, automation completion, human review, error/rework, cycle time, throughput, cost per completed case, and user feedback. Compare by case complexity rather than hiding hard cases in an average.

Calculate conservative, expected, and optimistic annual value, including ongoing costs. End with one of four decisions: stop, redesign, extend the pilot, or scale. State the evidence threshold and owner for the next decision. The purpose of a pilot is to reduce uncertainty, including the possibility that the right answer is not to proceed.
