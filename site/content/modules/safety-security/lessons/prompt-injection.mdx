In Module 3 you learned SQL injection: data concatenated into commands can be executed as commands, and parameterization creates a structural boundary. LLM prompts do not provide an equivalent guaranteed boundary between instructions and untrusted data. Roles, delimiters, and clear prompts improve ordinary instruction following, but any text the model processes can still influence its output. That is prompt injection, and it requires system-level controls rather than prompt wording alone.

The anatomy generalizes. An attacker plants instructions in content your system will process: an email, a résumé, a webpage, a PDF, a support ticket:

- *Direct injection:* the user themselves types "ignore your instructions and…"
- **Indirect injection** (the dangerous one): the payload hides in *third-party content* the model reads on a trusted user's behalf: white text in a document, an HTML comment on a webpage, a field in an uploaded file. Your user is innocent; the document is the attacker.

## Why you can't filter your way out

The instinctive defenses fail structurally:

- *"Detect malicious instructions"*: injections can be paraphrased, encoded, translated, or split across chunks; a classifier catches yesterday's phrasings. You're in an arms race with unbounded attacker creativity.
- *"Tell the model to ignore embedded instructions"*: helps at the margin; fails against exactly the adversary who tried twice. **A prompt is not a security boundary.**
- Delimiting data sections (Module 8) is necessary hygiene, but it is not sufficient.

The professional posture: **assume injection succeeds sometimes, and design so that a hijacked model can't do serious harm.** Security lives in what the model *can do*, not in what it's *told*.

## The lethal trifecta

Memorize this triangle. An AI system becomes *seriously* dangerous when it combines all three:

1. **Access to private data** (inbox, files, database)
2. **Exposure to untrusted content** (documents, web, incoming email)
3. **Ability to communicate externally** (send email, call APIs, post)

Injection enters through (2), harvests through (1), exfiltrates through (3). Break any leg and the classic data-theft attack collapses. Many real products need only two of the three: the summarizer doesn't need send-capability; the drafting assistant can require human send-approval, which converts leg (3) into a gated action.

## Map trust before testing prompts

Classify every token by origin: developer instruction, authenticated user input, retrieved document, web content, tool result, memory, image/OCR, or generated intermediate text. Only application-controlled policy has authority. Everything else may contain adversarial instructions, whether maliciously planted or accidentally quoted. Indirect injection arrives through data the user never typed, and multimodal inputs can hide text from casual review.

Describe the consequence path, not just the jailbreak. Injection becomes serious when the model can access sensitive data, communicate externally, or take consequential action. Record which source can influence which model decision and which capabilities are reachable from that decision. The same malicious string has different risk in a read-only summarizer and an email-sending agent with a confidential inbox.

Red-team tests must assert outcomes: Was secret data exposed? Was an unauthorized tool called? Did cited evidence become corrupted? Merely observing that the model repeated hostile text does not measure impact.

## Guided lab: build an attack corpus

Create 30 attacks across direct instructions, retrieved documents, tool outputs, encoded or obfuscated text, conflicting authority claims, data exfiltration requests, and multi-step social engineering. Include benign strings that resemble attacks to measure false positives.

Run them against a read-only assistant and a tool-enabled workflow. Record attack success by consequence, not by wording. For each successful path, identify the missing control outside the model. Keep this corpus as a regression suite for later defenses and model changes.
