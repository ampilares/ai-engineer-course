You will deliver one small software change and prove what it does. AI can accelerate reading and editing code, but the acceptance criteria, runtime permissions, and review remain engineering responsibilities. Business owners use the same process with a smaller implementation surface.

Start with a reproducible problem. "Improve the report" does not identify a defect. "Reject duplicate IDs with conflicting amounts instead of counting the first row" names an observable behaviour. Write a failing example, expected result, affected boundary, and a way to test it before asking for implementation.

Provide the repository entry point, relevant files, test command, constraints, and finish criteria. Ask the coding tool to inspect these files and explain the proposed change. A focused diff is easier to assess than a broad rewrite mixed with unrelated formatting.

A useful task brief for this week's exercise is:

```text
The report must identify conflicting duplicate transaction IDs.
Read the supplied reference implementation and its tests.
Explain the current behaviour before proposing a change.
Add a conflict case in a separate fixture copy.
Reject the conflicting event; preserve both source rows in review evidence.
Do not change the accepted treatment of exact duplicate copies.
Run the relevant tests and show the resulting diff.
Do not install new dependencies or contact external services for this task.
```

The boundaries are deliberately narrow. If the implementation needs a dependency, discuss its purpose and provenance instead of accepting an invented package name. If the assistant claims a test passed, inspect the command and output. Reading a test file is not running it.
