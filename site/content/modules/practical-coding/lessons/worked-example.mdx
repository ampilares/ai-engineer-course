Review in layers. First check the specification: does the change solve the intended problem? Then check inputs and edge cases. Then examine failure handling, data access, and side effects. Finally inspect maintainability: naming, duplication, and whether future readers can find the rule.

A meaningful regression test fails on the old broken behaviour and passes after the fix. Asserting that a function returns something is weak evidence. A test that inserts two rows with the same ID and different amounts, then verifies both are excluded and a conflict is visible, tests the business requirement.

Do not trust a generated test merely because it agrees with generated code. Derive expected results from the requirement. If the assistant implements an incorrect rule and writes a test expecting that rule, green tests can reinforce the mistake. Use a manually checked counterexample and ask a reviewer to challenge it.
