This week prepares the system for a limited pilot. A useful deployment has an owner, a budget, observable failure, and a way back to the manual process. A successful installation is only one part of readiness.

Separate development, test, and pilot environments. Keep their credentials and data distinct. Record the deployed code, prompt, model identifier when visible, retrieval snapshot, tool configuration, and permission policy. A change to a provider's model routing may affect behaviour even when your own code is unchanged.

Choose a small set of signals: task success, unsupported-answer rate, intervention rate, oldest waiting item, end-to-end latency, and cost per completed case. Define what each measures and how often someone checks it. A server returning HTTP 200 does not establish that the business task succeeded.

A service-level indicator is a measured property. An objective is a target for that property over a stated window. For example, "at least 95% of eligible report requests produce a checked draft within ten minutes during the pilot" names a population, outcome, duration, and window. It is a proposed classroom target, not a universal requirement. [Google's SRE chapter](https://sre.google/sre-book/service-level-objectives/) provides the underlying distinction.

<Check question={"In the objective about report requests, which phrase names the population being measured?"} options={["Eligible report requests","Within ten minutes","At least 95%","During the pilot"]} answer={0} explanation={"A good objective says who or what is counted, the outcome, the duration and the window. Eligible report requests is the population; the others are the target, duration and window."} />

Set stop conditions before rollout: an unauthorised action, a privacy boundary failure, spend beyond the agreed cap, or repeated missed deadlines. Stopping new work is different from cancelling work already in progress. Record how to inspect pending actions, revoke tool access, preserve evidence, and return users to a manual queue.

### Deployment checklist as an operating exercise

Confirm secrets are outside the repository, logs are appropriate, backups can be restored, and dependencies are recorded. Rehearse recovery with fictional data. A backup that has never been restored is unverified. Ask a second person to follow the runbook without your help; their questions reveal missing operational knowledge.
