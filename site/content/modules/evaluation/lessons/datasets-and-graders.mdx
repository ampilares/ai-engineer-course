An eval is only as honest as its dataset and only as scalable as its graders. This lesson builds both.

## The dataset: representative, adversarial, alive

Start with 30–50 examples; grow continuously. Source them from reality, not imagination:

- **Real traffic**: sampled inputs from production (or the pilot), stratified across the segments that matter (Module 5's habit: by customer type, document format, language).
- **The failure museum**: every production failure becomes a permanent eval case. This is the compounding loop: each bug fixed is a bug that can never silently return.
- **Edge cases and adversarial inputs**: empty documents, wrong-language emails, prompt-injection attempts, the unanswerable questions from Module 9.

Keep the dataset **versioned** (it's code), and split it mentally the way Module 5 taught: the set you iterate against daily, and a held-out slice you check rarely, because a prompt tuned against the same 50 examples for weeks has quietly overfit to them.

## Graders: three tiers, cheapest first

1. **Code checks**: exact and free. Schema validity, required fields, length caps, citation presence, the abstention phrase, forbidden content. A surprising share of "quality" is checkable this way; always exhaust this tier first.
2. **Reference comparison**: when a gold answer exists (extraction, classification), compare structurally: field-by-field, order-insensitive where appropriate.
3. **LLM as judge:** For open-ended qualities such as faithfulness, tone, or helpfulness, ask a model to grade outputs against a written rubric. Grade one criterion at a time and prefer a small, well-defined scale over an ambiguous 1–10 score. Model judges make large evaluation runs practical, but they are also probabilistic systems, so:

**Calibrate the judge before trusting it.** Grade 30–50 outputs yourself; run the judge on the same set; measure agreement. Below ~85–90%, fix the rubric or the judge prompt: don't deploy a grader that disagrees with you. And know the standard judge biases: preferring longer answers, preferring its own model family's phrasing, position bias in A/B comparisons (mitigate by randomizing order and grading criteria separately).

## Wiring it into the pipeline

The full loop, which is the module project: dataset in Git → runner executes your real system → graders score → report compares to the last baseline → **CI gate**: critical criteria regression blocks the merge. Failures link to their traces (next lesson) so "score dropped" turns into "these six examples broke, here's each one's trace."

<Callout type="tip">
Grade **stages separately** wherever your system has them: retrieval vs. generation (Module 9), extraction vs. routing (Module 13). End-to-end scores tell you *that* something broke; stage scores tell you *what*.

## Dataset quality is an engineering discipline

Sample from real traffic by time, source, user segment, difficulty, and outcome; do not let the most vocal failure mode become the entire set. Deduplicate near-identical cases and separate development, regression, and held-out samples. Version examples and labels append-only where possible. When an expected answer changes because policy changed, record effective dates rather than silently editing the past.

Human grading needs a rubric with observable criteria and examples at decision boundaries. Measure agreement on an overlap sample. Disagreement can expose an ambiguous rubric or genuinely subjective task; neither is solved by forcing one label without discussion.

An LLM judge should receive only the information required to grade and should return criterion-level reasoning or evidence plus a score. Test order bias, verbosity bias, self-preference, prompt injection inside candidate outputs, and performance by segment. Calibrate against blinded human labels and route uncertain or high-impact cases to people.

## Guided build: validate the grader

Create a rubric with at least three criteria and grade 40 outputs using deterministic checks where possible, two human raters on an overlap set, and an LLM judge. Include deliberately fluent-but-wrong, terse-but-correct, injected, and borderline examples.

Report human agreement, judge agreement with the adjudicated labels, false-pass and false-fail rates, segment performance, and cost. Choose an operating threshold and manual-review zone. The judge is acceptable only for the decisions its validation supports; a convenient score is not evidence of validity.
