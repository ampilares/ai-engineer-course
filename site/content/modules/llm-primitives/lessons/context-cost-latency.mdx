A feature that costs $0.002 per call is a rounding error in a demo and a $6,000/month line item at 100k calls/day. Cost and latency engineering isn't optimization theater: it decides which AI products are economically possible at all. The good news: Module 7 gave you the mechanics; this lesson turns them into levers.

Work through your own numbers and internalize the hierarchy the widget demonstrates:

1. **Output tokens dominate**: ~5× the price of input and the source of nearly all latency (one forward pass each). *Asking for shorter outputs is the cheapest optimization in existence*: request the JSON only, cap verbosity, skip the pleasantries.
2. **Prompt caching can materially reduce repeated-input cost.** Many providers discount eligible cached prefix tokens, but eligibility, retention, and discount rates vary. Place stable instructions, schemas, and examples before variable request data when the provider's caching rules support that structure. Confirm savings from usage records and current pricing rather than assuming a fixed percentage.
3. **Model tiering beats model loyalty.** Route the easy 80% (classification, routing, cleanup) to a small cheap model; save the frontier model for the hard 20%. Your evaluation set in Module 14 identifies the quality boundary with evidence.

## Latency: what the user feels

- **Time-to-first-token (TTFT)**: dominated by prefill (prompt length) and queueing.
- **Generation time**: output length × per-token time. Long answers *are* slow answers.

The main engineering levers are to generate fewer tokens, stream when users benefit from progressive output, parallelize independent calls, use smaller models on latency-sensitive paths, move suitable work to asynchronous processing, and set timeouts with product-appropriate fallbacks. Measure both time to first useful output and time to completion because streaming improves perceived responsiveness without reducing total work.

## Budgets are architecture

Decide *before building*: cost per task ≤ €X, p95 latency ≤ Y seconds. These constraints pick your models, prompt sizes, and caching strategy, not the other way around. And meter from day one: log tokens and cost per request, aggregated by feature. A recursive summarizer with no cost cap is a credit-card incident with extra steps; per-feature budgets with alerts are the smoke detector.

## Budget the full request path

Token price is only one cost. Include embeddings, reranking, retries, tool calls, moderation, storage, human review, and idle capacity for self-hosted models. Express economics per completed business outcome, not per API call. A cheaper model that doubles review work or retry rate can be more expensive overall.

Break latency into queue time, network connection, provider time to first token, generation time, tool execution, and validation. Percentiles matter: p95 and p99 expose the slow users hidden by an average. Set an end-to-end deadline, then allocate a budget to each stage. Parallelize independent retrieval or tool calls, but bound concurrency so one traffic spike does not create rate-limit failures.

Cache only when the reuse key is correct. Include relevant model, prompt, schema, permissions, and source-data version. Never let one tenant’s cached answer serve another. Semantic caching has a higher false-hit risk than exact caching and needs task-specific evaluation.

## Guided build: cost and latency envelope

For your structured worker, estimate low, typical, and high input/output token counts and monthly volume. Add retry and human-review rates. Calculate cost per accepted item and the break-even volume against the manual process.

Instrument 50 calls and report p50/p95 total latency plus stage timings. Test a smaller model, shorter context, exact cache, and bounded parallelism one at a time. Choose a configuration that meets an explicit quality floor, p95 target, and monthly budget. Record the rejected options and why; architecture is the set of trade-offs you can defend.
