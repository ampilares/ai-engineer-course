This week turns a set of demonstrations into a release decision. Define acceptable behaviour before looking at final results. A test suite is useful when it can reveal a reason not to release.

Keep development cases separate from final assessment cases. Use development cases to change prompts, tools, and retrieval. Freeze the held-out set before final evaluation. If you inspect a held-out failure and tune to it, that case becomes development evidence; create fresh cases for the next independent assessment.

The course supplies twenty development and ten held-out cases for practice. They are public, so a formal assessment needs independently authored variants. Include common cases, ambiguous inputs, missing evidence, changed sources, access restrictions, and action boundaries. Use actual users' case distribution when assessing a real pilot, while testing rare consequential failures separately.

Measure end-to-end task success with a denominator. Separately count invalid outputs, wrong decisions, unsupported claims, interventions, and unauthorised actions. A single number can hide a system that answers easy cases beautifully and fails critical ones. Time out or cancelled cases belong in the attempted-case denominator unless the protocol predefines a different exclusion.

For subjective outputs, write a rubric with observable anchors. "Good report" is vague. "Every numerical claim reconciles; every policy claim cites an effective authorised passage; unresolved items remain visible" is reviewable. An LLM grader can scale some checks, but first compare its decisions with human labels. [OpenAI's evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices#llm-as-a-judge-and-model-graders) identifies limitations including response-order and verbosity bias.
