### Engineering route

1. Run the reference evaluator on a saved prediction file. Inspect missing, duplicate, and extra IDs as well as incorrect labels.
2. Freeze your capstone's development/held-out split and versions.
3. Run boundary tests for access, tool scope, approvals, cancellation, stale sources, and log exposure.
4. Inspect a trace for the most consequential failure, change one component, and repeat affected regression cases.
5. Produce a release record stating pass, hold, or restricted pilot, with evidence for every mandatory condition.

### Business-owner route

1. Write acceptance criteria before inspecting the final outputs. Identify failures that always require a hold.
2. Independently grade a sample of results and compare with the system's automatic checks.
3. Review who can access data, which vendors process it, which permissions are needed, and how access is removed.
4. Name an owner for incident response, retention, complaints, and changes to the workflow.
5. Decide whether the system is acceptable for a bounded pilot and document the restrictions.

### Expected evidence

Submit the cases, rubric, version record, results with denominators, two reviewed traces, boundary-test evidence, and a release decision. Classroom thresholds are not guarantees of production safety. Larger or higher-consequence deployments require an evaluation designed for the actual stakes and operating conditions.

Use [the release record](/course-materials/course/templates/release-record.md). If legal, regulatory, or contractual requirements affect the pilot, identify the appropriate organisational reviewer and record their decision rather than inventing a generic compliance claim.
