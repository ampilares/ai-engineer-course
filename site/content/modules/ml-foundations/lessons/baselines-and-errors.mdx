The fastest way to waste a month in ML is to start with the fanciest model. The professional move is the opposite: establish a **naive baseline** in an hour, then let evidence justify every step of added complexity.

## Baselines: the floor you must beat

A baseline is the simplest thing that could possibly work:

- Classification: always predict the most common class.
- Regression: always predict the mean (or last observed value).
- Churn: "customers inactive 30+ days will churn."

Baselines are cheap insurance against two failure modes. If your model barely beats the baseline, the features carry little signal: no amount of architecture fixes that. And if the *baseline itself* solves the business problem… ship the baseline; it has no training pipeline to maintain, no drift to monitor, and no GPU bill.

## The classical toolbox that refuses to die

For tabular business data (the majority of real problems), the winning tools are unglamorous:

- **Linear/logistic regression**: fast, interpretable coefficients, hard to beat when relationships are roughly additive. Always a strong second baseline.
- **Decision trees**: human-readable if/else splits; prone to overfitting alone…
- **Gradient-boosted trees and random forests:** These ensembles are strong baselines for tabular data and often outperform deep learning when the dataset is structured and not extremely large. Compare them rather than assuming one family will always win.

Deep learning (next module) earns its keep on *unstructured* data (images, audio, and text) where features can't be hand-listed. Knowing which world you're in is a core engineering judgment.

## Error analysis: where the improvement actually lives

A single metric says *how much* the model errs; it never says *why*. The highest-leverage hour in any ML project is reading errors: individually and **by segment**:

```text
overall error:            9%
  new customers:         23%   ← the problem lives here
  existing customers:     6%
  mobile submissions:    19%   ← and here
  desktop submissions:    7%
```

An aggregate 9% looked fine; the breakdown reveals the model is failing specific populations: perhaps features are missing for new customers, perhaps mobile photos are blurry. Each hypothesis suggests a *data* fix, which usually beats a *model* fix.

## Build the improvement ladder

Use a sequence that makes every added complication earn its place:

1. **Business baseline:** the current rule, human process, or “do nothing” outcome.
2. **Naive statistical baseline:** majority class, last value, mean, or simple keyword rule.
3. **Interpretable model:** logistic/linear regression or a shallow tree.
4. **Strong tabular model:** a well-tuned boosted-tree pipeline.
5. **Specialized complexity:** deep learning only if the data type, volume, and measured gap justify it.

Keep the split and metric fixed while moving up the ladder. Otherwise you cannot attribute improvement. Include inference time, maintenance burden, explanation needs, and data requirements in the comparison; one extra metric point may not pay for a system that is ten times harder to operate.

Error analysis turns the next iteration into evidence. Sample false positives and false negatives, add reason codes, and group them. Common buckets include ambiguous labels, missing context, data quality, distribution shift, and a genuinely hard boundary. Fix label or pipeline defects before tuning the model around them.
