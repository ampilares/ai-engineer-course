Your AI system *will* have bad days: a provider outage, a silent quality regression, a prompt change that broke edge cases, a cost spike. Maturity isn't preventing all incidents: it's detecting them fast, recovering cleanly, and learning so each one can't recur. This lesson turns "everything's on fire" into a procedure.

## The incident loop

**Detect → mitigate → diagnose → resolve → learn.** The order matters: mitigate *before* you fully understand.

- **Detect**: monitoring and alerts (Module 14) catch it before users report it: error-rate spikes, latency breaches, cost anomalies, correction-rate jumps. A metric moving is your pager.
- **Mitigate first**: stop the bleeding before diagnosing. The fastest mitigation is almost always **rollback**: revert to the last known-good version (config or code) in seconds. A working old version beats a broken new one you're still debugging. Also in the kit: disable the affected feature (graceful degradation), flip to a fallback model, or throttle.
- **Diagnose:** Use traces from Module 14 to find the root cause after containment has stopped active harm. Versioned prompts, models, datasets, and configuration turn "what changed?" into an evidence-based comparison.
- **Resolve**: fix forward with the fix validated by your eval suite, re-deploy behind a canary.
- **Learn:** Write a blameless incident review covering what happened, why the controls allowed it, and how detection and response should improve. Turn the failure into a permanent evaluation case so the same regression is detected before a future release.

## Prerequisites you built all course

Fast, safe incident response isn't heroics: it's the payoff of habits from earlier modules, assembled:

- **Versioned everything** (Module 3): rollback and "what changed?" require it.
- **One-command deploy + rollback** (this module): mitigation speed is a technical capability you build *before* the incident.
- **Traces and monitoring** (Module 14): detection and diagnosis.
- **Eval suite** (Module 14): validates the fix and immortalizes the failure.
- **Graceful degradation + fallbacks** (this module): mitigation options beyond rollback.

Write the **runbook** before you need it: how to roll back, how to disable each feature, who to notify, where the dashboards are, how to restore from backup. An incident at 2am is the wrong time to invent the procedure.

## AI incidents span more than code

A regression may originate in model routing, provider behavior, prompt/config, tool schema, source data, parser, embedding index, authorization, or traffic mix. Your change inventory and traces must identify each version. Rollback may mean restoring a prompt, disabling a tool, switching a model alias, republishing an index, stopping ingestion, or routing work to humans.

Preserve evidence while minimizing sensitive exposure: correlation IDs, versions, affected population, safe samples, decisions, and side-effect receipts. Severity depends on consequence and blast radius, not whether the HTTP service stayed up. A fast wrong answer can be a more serious outage than a visible error.

After containment and recovery, write a blameless analysis of conditions and controls. Action items should change the system, test, alert, isolation, limit, runbook, ownership, not merely ask people to be more careful. Add the failure to the regression set and verify the prevention mechanism.

## Guided exercise: run an incident game day

Choose one scenario: cross-tenant retrieval, silent extraction regression, runaway tool loop, stale policy index, or duplicate external action. Assign incident lead, operations, communications, and subject-matter roles. Inject incomplete information and time pressure.

Measure time to detect, classify, contain, recover, and verify. Produce a timeline, impact estimate, rollback evidence, stakeholder update, and post-incident review with owned deadlines. Re-run the scenario after fixes and demonstrate a faster or automatically prevented outcome.
